# Specs: Case Types — V1 Delta

This file specifies requirements for the V1 completion of the Case Types change.
The canonical spec is at `openspec/specs/case-types/spec.md` (REQ-CT-01 through REQ-CT-16).
This delta adds requirements for the missing V1 admin tabs, backend validation enforcement,
and seed data, derived from the two market features:

1. **Zaaktype (Case Type) Management** — demand 603, 199 tender mentions
2. **Select case type to initiate the correct BPMN process** — demand 18, 6 tender mentions

---

## Stakeholders

**Municipal Administrator (Gemeentebeheerder)**
- Configures case types and their sub-entities in the admin settings panel
- Responsible for archival compliance (Archiefwet/Selectielijst), role definitions, and document checklists
- Goal: Configure a new case type end-to-end without needing developer support

**Case Handler (Behandelaar)**
- Creates and processes cases; selects a case type to start a case
- Relies on case type configuration for valid statuses, required fields, and allowed roles
- Goal: Follow a guided process that enforces the correct workflow for each case type

**Process Manager (Procesmanager)**
- Designs and links BPMN workflow templates to case types
- Ensures the correct automated process initiates when a case is created
- Goal: Case types act as entry points for BPMN workflow initiation

---

## User Stories

**US-CT-01**: As a municipal administrator, I want to define result types with archival rules
per case type so that closed cases are retained or destroyed according to the Archiefwet.

**US-CT-02**: As a municipal administrator, I want to define role types per case type so that
only appropriate participant roles appear when assigning case participants.

**US-CT-03**: As a municipal administrator, I want to define property definitions per case type
so that handlers are prompted to fill in domain-specific data fields at the right lifecycle stage.

**US-CT-04**: As a municipal administrator, I want to define required document types per case type
so that handlers cannot advance a case without uploading the necessary documents.

**US-CT-05**: As a municipal administrator, I want the publish action to be validated server-side
so that incomplete case types cannot be published through the API even without the UI guard.

**US-CT-06**: As a case handler, I want the system to prevent deletion of a case type that has
active cases so that live cases are never left without a valid type reference.

---

## Customer Journeys

**Journey 1 — Admin Configures a New Case Type End-to-End**

Trigger: New municipal process requires a configured case type before handlers can create cases.

1. Admin navigates to Procest → Admin Settings → Case Types → "Add Case Type"
2. Admin fills in General tab (title, purpose, trigger, deadline, etc.) and saves as draft
3. Admin switches to "Statuses" tab, adds 4 ordered status types, marks last as final
4. Admin switches to "Results" tab, adds 3 result types with archival rules
5. Admin switches to "Roles" tab, adds 4 role types with generic role assignments
6. Admin switches to "Properties" tab, adds custom fields with format and status gate
7. Admin switches to "Docs" tab, adds required document types with direction and status gate
8. Admin clicks "Publish" — backend validates completeness and sets `isDraft = false`
9. Case type becomes available to handlers in the case creation form

Pain point resolved: Previously, admins could not configure V1 sub-entities (results, roles,
properties, docs) — they had to use raw API calls or wait for developer intervention.

**Journey 2 — Handler Creates a Case Selecting the Correct BPMN Workflow**

Trigger: Citizen submits a permit application via DSO or front desk.

1. Handler opens Procest → New Case
2. Handler selects case type "Omgevingsvergunning" from the dropdown
3. System auto-assigns the bound `workflowTemplate` to the case
4. Status advances to "Ontvangen"; BPMN workflow engine initiates the first process step
5. Handler follows guided task list generated by the workflow

Pain point resolved: Without case type → workflow template binding, handlers must manually
start workflow steps, risking missed required tasks.

### REQ-CT-07: Result Type Management Tab

The system SHALL provide an admin tab for managing result types on a case type.
Result types define the allowed outcomes for cases of this type, with archival rules
compliant with the Archiefwet/Selectielijst.

**Feature tier**: V1

**Entities**: `resultType` (caseType: reference, name: string, description: string,
archivalAction: string, archivalPeriod: string, archivalStatus: string)
See ADR-000 `resultType` entity for full field list.

#### Scenario CT-07-01: View result types tab

- GIVEN an admin editing a case type "Omgevingsvergunning"
- WHEN they click the "Results" tab
- THEN the system MUST display all result types linked to this case type
- AND each row MUST show: name, archivalAction (retain/destroy badge), archivalPeriod (formatted)
- AND an "Add" button MUST be visible

#### Scenario CT-07-02: Add a result type with archival rules

- GIVEN an admin on the Results tab for case type "Omgevingsvergunning"
- WHEN they click "Add" and submit:
  - Name: "Vergunning verleend"
  - archivalAction: "blijvend_bewaren"
  - archivalPeriod: "P20Y"
- THEN the system MUST create a `resultType` OpenRegister object with `caseType` referencing the current case type
- AND the new result type MUST appear in the tab list

#### Scenario CT-07-03: Edit a result type

- GIVEN a result type "Vergunning verleend" with `archivalPeriod = "P20Y"`
- WHEN the admin changes `archivalPeriod` to "P25Y"
- THEN the result type MUST be updated in OpenRegister
- AND the change MUST apply to future case closures only

#### Scenario CT-07-04: Delete a result type

- GIVEN a result type "Aanvraag ingetrokken" not referenced by any closed cases
- WHEN the admin deletes it and confirms the dialog
- THEN the result type MUST be removed from OpenRegister
- AND the tab list MUST no longer show this result type

#### Scenario CT-07-05: Name is required

- GIVEN the result type creation form
- WHEN the admin submits with an empty name
- THEN the system MUST reject with: "Name is required"

### REQ-CT-08: Role Type Management Tab

The system SHALL provide an admin tab for managing role types on a case type.
Role types restrict which participant roles are available when assigning case participants.

**Feature tier**: V1

**Entities**: `roleType` (caseType: reference, name: string, description: string)
See ADR-000 `roleType` entity for full field list.

#### Scenario CT-08-01: View role types tab

- GIVEN an admin editing case type "Omgevingsvergunning"
- WHEN they click the "Roles" tab
- THEN the system MUST display all role types linked to this case type
- AND each row MUST show: name, description (truncated)
- AND an "Add" button MUST be visible

#### Scenario CT-08-02: Add a role type

- GIVEN an admin on the Roles tab for case type "Omgevingsvergunning"
- WHEN they click "Add" and submit:
  - Name: "Technisch adviseur"
  - Description: "Adviseert de behandelaar over technische aspecten van de aanvraag."
- THEN the system MUST create a `roleType` OpenRegister object linked to the current case type
- AND the new role type MUST appear in the tab list

#### Scenario CT-08-03: Role types restrict case participant roles

- GIVEN a case of type "Omgevingsvergunning" with role types ["Aanvrager", "Behandelaar", "Technisch adviseur"]
- WHEN a user opens the "Add participant" dialog on a case
- THEN the role dropdown MUST only show: Aanvrager, Behandelaar, Technisch adviseur
- AND the user MUST NOT be able to assign "Klager" (defined only for Klachtbehandeling)

#### Scenario CT-08-04: Edit a role type

- GIVEN a role type "Technisch adviseur"
- WHEN the admin renames it to "Externe adviseur"
- THEN the name MUST be updated in OpenRegister
- AND existing role assignments on cases MUST display the new name

#### Scenario CT-08-05: Delete a role type

- GIVEN a role type "Beslisser" not assigned on any active cases
- WHEN the admin deletes it
- THEN the role type MUST be removed from the case type

### REQ-CT-02b: Backend Publish Validation

The system MUST enforce publish prerequisites on the backend. Frontend-only validation
is insufficient as the API can bypass it. Server-side enforcement prevents incomplete
case types from reaching production.

**Feature tier**: MVP — enforcement gap

**Entities**: `caseType`, `statusType`

#### Scenario CT-02b-01: Publish blocked — no status types

- GIVEN a draft case type "Testtype" with no linked status types
- WHEN the API receives a PATCH/PUT setting `isDraft = false`
- THEN the server MUST return HTTP 422 with:
  ```json
  { "errors": ["At least one status type must be defined before publishing"] }
  ```
- AND the case type MUST remain in draft state

#### Scenario CT-02b-02: Publish blocked — no final status type

- GIVEN a draft case type with 2 linked status types, neither has `isFinal = true`
- WHEN the API attempts to publish
- THEN the server MUST return HTTP 422 with:
  ```json
  { "errors": ["At least one status type must be marked as final"] }
  ```

#### Scenario CT-02b-03: Publish blocked — validFrom not set

- GIVEN a draft case type with valid status types but `validFrom` is null/empty
- WHEN the API attempts to publish
- THEN the server MUST return HTTP 422 with:
  ```json
  { "errors": ["'Valid from' date must be set before publishing"] }
  ```

#### Scenario CT-02b-04: Publish succeeds with all prerequisites met

- GIVEN a draft case type with: 3 status types (one `isFinal = true`), `validFrom = "2026-01-01"`,
  all required fields filled (title, purpose, trigger, subject, processingDeadline, origin,
  confidentiality, responsible)
- WHEN the API sets `isDraft = false`
- THEN the server MUST return HTTP 200 with the updated case type
- AND `isDraft` MUST be `false` in the response

#### Scenario CT-02b-05: Multiple validation errors returned together

- GIVEN a draft case type with no status types and no `validFrom`
- WHEN the API attempts to publish
- THEN the server MUST return HTTP 422 with BOTH errors in the `errors` array
- AND the admin UI MUST display all errors simultaneously

### REQ-CT-01d: Active Case Deletion Blocking

The system MUST prevent deletion of a case type that has active (non-final) cases.
This protects live cases from losing their type reference.

**Feature tier**: MVP — enforcement gap

**Entities**: `caseType`, `case`

#### Scenario CT-01d-01: Deletion blocked — active cases exist

- GIVEN a case type "Omgevingsvergunning" with 7 active cases (non-final status)
- WHEN the admin attempts to delete the case type (via UI or API)
- THEN the server MUST return HTTP 409 with:
  ```json
  { "message": "Cannot delete case type 'Omgevingsvergunning': 7 active cases are using this type. Close or reassign all cases first." }
  ```
- AND the case type MUST remain in OpenRegister

#### Scenario CT-01d-02: Deletion warned — only closed cases exist

- GIVEN a case type "Testtype" with 0 active cases and 3 closed cases
- WHEN the admin attempts to delete
- THEN the system MUST display a confirmation dialog:
  "This case type is referenced by 3 closed cases. Deleting it will remove the type reference from those cases. Continue?"
- AND if confirmed, the deletion MUST proceed

#### Scenario CT-01d-03: Deletion succeeds — no cases

- GIVEN a case type "Ongebruikt Type" with no associated cases
- WHEN the admin deletes it and confirms the `CnDeleteDialog`
- THEN the case type MUST be deleted from OpenRegister
- AND all linked sub-entities (statusType, resultType, roleType, propertyDefinition,
  documentType, decisionType) MUST also be deleted

### REQ-CT-17: Case Type Seed Data

The system SHALL provide pre-seeded realistic Dutch case types imported via the repair step.
Seed data enables automated browser testing and manual QA without requiring manual setup.

**Feature tier**: MVP — on-install completeness

**Entities**: `caseType`, `statusType`, `resultType`, `roleType`

#### Scenario CT-17-01: Seed data imported on first install

- GIVEN a fresh Procest installation running the repair step for the first time
- WHEN `ConfigurationService::importFromApp('procest', data, version, false)` is called
- THEN the following case types MUST exist in the `procest` register:
  - "Omgevingsvergunning" (processingDeadline: P56D, isDraft: false)
  - "Subsidieaanvraag" (processingDeadline: P13W, isDraft: false)
  - "Klachtbehandeling" (processingDeadline: P6W, isDraft: false)
  - "Bezwaarschrift" (processingDeadline: P6W, isDraft: false)
- AND each case type MUST have at least 3 linked status types (one with `isFinal = true`)
- AND each case type MUST have at least 3 linked result types

#### Scenario CT-17-02: Seed data is idempotent

- GIVEN an installation where seed data was already imported
- WHEN the repair step runs again (e.g., after an update)
- THEN the system MUST NOT create duplicate case types
- AND existing customisations to the seeded case types MUST be preserved
- AND no errors MUST be thrown

#### Scenario CT-17-03: Seed case types are publishable

- GIVEN the 4 seeded case types
- WHEN the backend publish validation runs against each (REQ-CT-02b)
- THEN all 4 MUST pass validation without errors
  (each has: ≥1 status type, ≥1 isFinal status type, validFrom set)
